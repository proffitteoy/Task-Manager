# 阶段五：系统优化与产品化打磨文档

## 1. 阶段定位

阶段五不是继续堆功能，而是把前四阶段已经跑通的全流程工作站变成一个稳定、清晰、可维护、可长期使用的产品。

前四阶段解决的是：

```bash
能不能跑起来
能不能整合 Homepage / ActivityWatch / Mineradio / 任务 / 计时 / 统计 / 复盘
能不能让用户配置
能不能 Docker 和 Windows 发布
```

阶段五解决的是：

```bash
跑久了会不会乱
数据库会不会爆
哪些数据该保留
哪些数据该丢弃
哪些信息应该落成字段
哪些信息应该放 JSON
哪些信息只做缓存
哪些信息不应该存
前端文案是否清楚
UI 是否统一
用户是否知道自己在干什么
系统是否可调试、可迁移、可恢复
```

阶段五的核心目标是：

```bash
让系统从“可用”变成“长期可用”。
```

## 2. 优化总原则

### 2.1 不为幻想中的功能提前复杂化

系统里所有数据结构、字段、索引、设置项都必须服务于已经存在或近期明确会做的功能。

不允许为了“以后可能有用”无限保留原始数据。

### 2.2 保留事实，丢弃噪音

应该长期保留的是：

```bash
用户主动创建的内容
任务和项目
计时结果
每日复盘
用户设置
最终统计结果
可解释的调整记录
```

应该短期保留的是：

```bash
原始 ActivityWatch 窗口标题
原始浏览器标题
原始音乐搜索结果
API 原始响应
调试日志
临时缓存
失败重试记录
```

不应该保存的是：

```bash
明文音乐平台 Cookie
敏感 token
无意义的完整网页标题长期历史
过细粒度的鼠标键盘数据
无法解释的临时中间状态
重复的大型原始 payload
```

### 2.3 业务核心字段结构化，外部原始数据 JSON 化

频繁查询、排序、筛选、关联的数据必须落成字段。

第三方 API 原始响应、临时配置、扩展数据可以放 JSON。

判断标准：

```bash
会不会经常用 WHERE 查？
会不会经常排序？
会不会用于关联？
会不会用于统计？
会不会用于唯一约束？
会不会出现在 UI 主要列表中？
```

如果答案是“是”，就应该落成字段。

如果只是为了保留外部接口原貌，放 JSON。

### 2.4 用户可以改，系统要留下痕迹

计时器、任务归属、时间分割允许用户手动调整。

但调整必须记录：

```bash
原始值
修改后值
修改时间
修改原因
修改来源
```

这不是为了限制用户，而是为了让每日复盘可信。

### 2.5 默认本地优先，默认隐私保守

系统默认只保留必要信息。

高敏感信息默认短期保存或不保存。

ActivityWatch、音乐登录态、token/GitHub 统计都要有清晰的数据说明。

## 3. 数据分层设计

系统数据分为六层：

```bash
L0 临时运行态
L1 缓存数据
L2 原始采集数据
L3 标准化事件数据
L4 业务事实数据
L5 聚合统计数据
```

### 3.1 L0 临时运行态

只存在内存中，不进数据库。

包括：

```bash
当前播放进度
当前窗口尺寸临时状态
当前拖拽中的 widget 位置
未提交表单内容
当前 WebSocket 连接状态
当前 hover / selected UI 状态
```

不应入库。

### 3.2 L1 缓存数据

可以丢弃，可以重建。

包括：

```bash
GitHub API 原始响应缓存
Tokei 统计原始输出缓存
音乐搜索结果缓存
歌词缓存
封面缓存
ActivityWatch 查询结果缓存
天气结果缓存
```

特点：

```bash
允许过期
允许清理
不作为事实来源
不参与核心复盘
```

### 3.3 L2 原始采集数据

短期保留，用于回溯和调试。

包括：

```bash
ActivityWatch 原始 buckets
GitHub contribution 原始 calendar
Tokei 原始 daily costs
音乐播放原始 provider payload
计时器原始操作事件
```

特点：

```bash
保留周期有限
可能包含敏感信息
不直接展示给用户
会被加工成 L3/L4/L5
```

### 3.4 L3 标准化事件数据

系统内部统一格式的数据。

包括：

```bash
task.created
task.started
timer.started
timer.stopped
timer.adjusted
activity.afk.detected
music.track.changed
github.activity.refreshed
token.usage.refreshed
review.closed
```

特点：

```bash
格式统一
可用于调试
可用于恢复部分状态
可用于生成时间线
```

### 3.5 L4 业务事实数据

长期保留，是系统最重要的数据。

包括：

```bash
项目
任务
计时 session
计时 segment
每日复盘
用户设置
手动调整记录
用户主动创建的笔记
```

特点：

```bash
不能轻易删除
需要 migration
需要导入导出
需要备份
```

### 3.6 L5 聚合统计数据

长期保留，用于趋势分析。

包括：

```bash
每日专注分钟
每日 AFK 分钟
每日 token 总量
每日 GitHub contribution
每日音乐播放分钟
每日项目时间分布
每日任务完成数
每周/月趋势
```

特点：

```bash
体积小
查询快
适合长期保留
可以由 L2/L3/L4 重建，但重建成本可能较高
```

## 4. 数据保留与丢弃策略

### 4.1 长期保留的数据

以下数据默认永久保留，除非用户手动删除：

```bash
projects
tasks
timer_policies
focus_sessions
focus_segments
daily_reviews
user_settings
widget_layouts
manual_adjustments
daily_activity_summary
```

原因：

```bash
这些是用户主动工作痕迹或最终统计结论。
删除后会破坏长期复盘。
```

### 4.2 中期保留的数据

默认保留 180 天到 365 天。

包括：

```bash
token_daily_usage
github_daily_activity
music_play_history
project_daily_summary
task_daily_summary
```

建议：

```bash
token_daily_usage：永久保留每日总量，明细保留 365 天
github_daily_activity：永久保留每日 count，原始 payload 保留 365 天
music_play_history：明细保留 180 天，按日聚合永久保留
```

### 4.3 短期保留的数据

默认保留 7 天到 30 天。

包括：

```bash
ActivityWatch 原始窗口标题
ActivityWatch 原始浏览器标题
原始 API payload
错误日志
调试日志
音乐搜索历史
天气查询缓存
```

建议：

```bash
activitywatch_raw_events：7 天
browser_title_raw_events：7 天
api_raw_cache：30 天
error_logs：30 天
debug_logs：7 天
music_search_history：30 天
weather_cache：1 天
```

### 4.4 只保留聚合，不保留明细的数据

对于敏感但有统计价值的数据，应当只长期保留聚合结果。

例如 ActivityWatch：

```bash
长期保留：
  VS Code 120 分钟
  Obsidian 80 分钟
  Browser 40 分钟
  AFK 15 分钟

短期保留：
  具体窗口标题
  具体网页标题
  具体 URL
```

这样既能复盘，又避免长期保存过多隐私信息。

### 4.5 不应入库的数据

以下数据原则上不入 SQLite：

```bash
音乐平台明文 Cookie
GitHub access token
系统级敏感凭据
完整音频文件
大型封面二进制
临时下载文件
高频鼠标键盘事件
未提交表单草稿
```

处理方式：

```bash
Cookie / token -> 系统安全存储或加密文件
封面 / 歌词 / 缓存 -> 文件系统 cache
未提交草稿 -> sessionStorage 或短期 local state
```

## 5. 字段化与 JSON 化规则

### 5.1 必须落成字段的信息

凡是核心业务查询条件，都必须落字段。

#### tasks

必须字段化：

```bash
id
project_id
title
status
source
planned_date
estimate_minutes
timer_policy_id
created_at
updated_at
completed_at
```

可以 JSON 化：

```bash
tags_json
context_json
external_ref_json
display_options_json
```

原因：

```bash
任务列表会频繁按 project_id、status、planned_date 查询。
这些不能只放 JSON。
```

#### focus_sessions

必须字段化：

```bash
id
task_id
project_id
policy_id
started_at
ended_at
planned_minutes
actual_minutes
effective_minutes
afk_minutes
status
created_at
updated_at
```

可以 JSON 化：

```bash
activity_evidence_json
music_context_json
adjustment_summary_json
```

原因：

```bash
计时 session 是统计和复盘核心。
时间、归属、状态必须字段化。
```

#### focus_segments

必须字段化：

```bash
id
session_id
type
started_at
ended_at
duration_seconds
source
```

可以 JSON 化：

```bash
metadata_json
```

segment type 建议：

```bash
focus
break
afk
manual
interruption
idle
```

#### daily_reviews

必须字段化：

```bash
id
date
summary
score
closed_at
created_at
updated_at
```

可以 JSON 化：

```bash
review_json
evidence_json
tomorrow_plan_json
```

#### activity_snapshots

必须字段化：

```bash
id
source
date
started_at
ended_at
created_at
```

可以 JSON 化：

```bash
payload_json
```

#### daily_activity_summary

必须字段化：

```bash
date
focus_minutes
effective_focus_minutes
afk_minutes
token_total
github_contribution_count
music_minutes
task_completed_count
session_count
created_at
updated_at
```

可以 JSON 化：

```bash
top_apps_json
top_projects_json
top_music_moods_json
raw_sources_json
```

### 5.2 可以 JSON 化的信息

适合 JSON 的信息：

```bash
第三方 API 原始响应
widget 个性化配置
主题细节参数
任务上下文扩展
外部服务引用
音乐 provider 特有字段
ActivityWatch 原始 bucket
复杂图表配置
```

但 JSON 里不应该埋关键查询字段。

错误示例：

```json
{
  "task": {
    "status": "done",
    "projectId": "math",
    "plannedDate": "2026-07-07"
  }
}
```

如果系统需要经常查 `status`、`projectId`、`plannedDate`，这些必须是字段。

### 5.3 字段冗余原则

允许适度冗余字段以提高查询效率。

例如 `focus_sessions` 中既有 `task_id`，也有 `project_id`。

原因：

```bash
任务可能被删除或移动项目。
session 的历史归属应该保持稳定。
统计项目时间时不应该总是 join tasks。
```

类似地，`daily_activity_summary` 可以冗余每日汇总结果。

## 6. 数据库优化

### 6.1 索引设计

第一批必要索引：

```sql
CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_project_id ON tasks(project_id);
CREATE INDEX idx_tasks_planned_date ON tasks(planned_date);
CREATE INDEX idx_tasks_timer_policy_id ON tasks(timer_policy_id);

CREATE INDEX idx_focus_sessions_task_id ON focus_sessions(task_id);
CREATE INDEX idx_focus_sessions_project_id ON focus_sessions(project_id);
CREATE INDEX idx_focus_sessions_started_at ON focus_sessions(started_at);
CREATE INDEX idx_focus_sessions_ended_at ON focus_sessions(ended_at);

CREATE INDEX idx_focus_segments_session_id ON focus_segments(session_id);
CREATE INDEX idx_focus_segments_started_at ON focus_segments(started_at);

CREATE INDEX idx_activity_snapshots_source_date ON activity_snapshots(source, date);
CREATE INDEX idx_daily_activity_summary_date ON daily_activity_summary(date);

CREATE INDEX idx_daily_reviews_date ON daily_reviews(date);
```

### 6.2 查询优化原则

首页 dashboard 不能每次加载都全表扫描。

首页需要的数据应来自 summary 表：

```bash
daily_activity_summary
today_task_summary
today_timer_summary
widget_state_cache
```

复杂统计应提前聚合。

例如：

```bash
不要每次打开首页都重新扫描全部 focus_segments。
应该在 session 结束时更新 daily_activity_summary。
```

### 6.3 写入策略

计时器运行中不应该每秒写数据库。

推荐：

```bash
内存中维护当前计时状态
每 30 秒 checkpoint 一次
暂停/结束/切 segment 时写入
应用关闭前 flush
```

避免：

```bash
每秒 UPDATE focus_sessions
每秒 INSERT timer_tick
```

### 6.4 日志表控制

不要无限制写 event log。

事件日志建议分级：

```bash
critical_events：长期保留
debug_events：7 天清理
sync_events：30 天清理
api_errors：30 天清理
```

### 6.5 Migration 规则

每次 schema 变更必须：

```bash
1. 写 migration
2. 写 rollback 说明
3. 写数据迁移脚本
4. 写兼容旧数据的读取逻辑
5. 更新 DATA_MODEL.md
```

禁止：

```bash
直接手改 SQLite
直接删除旧字段
不写迁移说明
```

## 7. 数据清理机制

### 7.1 自动清理任务

系统应内置每日清理任务。

默认每天凌晨执行：

```bash
cleanup:raw-activitywatch
cleanup:api-cache
cleanup:logs
cleanup:music-search-history
cleanup:weather-cache
compact:database
```

### 7.2 清理策略配置

用户可在设置中修改：

```yaml
retention:
  activitywatchRawDays: 7
  apiCacheDays: 30
  debugLogDays: 7
  errorLogDays: 30
  musicSearchHistoryDays: 30
  musicPlayHistoryDays: 180
  tokenRawDays: 365
  githubRawDays: 365
```

### 7.3 手动清理入口

设置页提供：

```bash
清理临时缓存
清理 ActivityWatch 原始明细
清理音乐搜索历史
清理 API 原始响应
清理调试日志
压缩数据库
```

### 7.4 清理前保护

自动清理不能删除：

```bash
任务
项目
计时 session
每日复盘
用户设置
长期 summary
用户主动笔记
```

## 8. 前端文本优化

### 8.1 文案原则

前端文案要避免技术味过重。

用户不需要看到：

```bash
activity_snapshots
focus_segments
payload_json
timer_policy
adapter
```

用户应该看到：

```bash
今日活动
专注记录
时间分割
计时规则
电脑活动
音乐场景
复盘证据
```

### 8.2 核心概念命名

建议命名：

```bash
Task -> 任务
Project -> 项目
Focus Session -> 专注记录
Segment -> 时间片段
Timer Policy -> 计时规则
Activity Evidence -> 活动证据
Daily Review -> 每日复盘
Workspace Mode -> 工作模式
Widget -> 组件
Mood -> 音乐氛围
```

### 8.3 页面标题

推荐：

```bash
今日工作站
任务
弹性计时
音乐
电脑活动
活动统计
每日复盘
设置
```

不推荐：

```bash
Dashboard
Workbench Core
Timer Policy Manager
Activity Snapshot Viewer
```

### 8.4 空状态文案

任务为空：

```bash
今天还没有任务。创建一个任务，或者直接开始一次自由计时。
```

计时器未启动：

```bash
还没有开始计时。选择一个任务，或直接开始一段专注时间。
```

ActivityWatch 未连接：

```bash
未检测到 ActivityWatch。你仍然可以使用任务和计时器，但电脑活动证据暂时不可用。
```

音乐未连接：

```bash
音乐服务未启动。你可以继续工作，稍后再启用音乐组件。
```

token 统计不可用：

```bash
暂时无法读取 token 统计。请检查 Tokei 路径和 Python 配置。
```

GitHub 统计不可用：

```bash
暂时无法读取 GitHub 活动。请检查用户名或网络状态。
```

### 8.5 操作按钮文案

推荐：

```bash
开始专注
暂停
继续
结束
拆分时间
补记时间
关联任务
切换任务
建议休息
跳过休息
进入复盘
保存调整
```

不推荐：

```bash
Start
Stop
Submit
Confirm
Execute
```

### 8.6 错误文案

错误文案必须说明：

```bash
发生了什么
影响是什么
用户可以怎么做
```

示例：

```bash
ActivityWatch 连接失败。电脑活动组件暂时不可用，但任务和计时器不受影响。请确认 ActivityWatch 已启动，并检查设置中的服务地址。
```

不要写：

```bash
Request failed.
Unknown error.
Something went wrong.
```

## 9. UI/UX 样式优化

### 9.1 整体视觉方向

项目主视觉应是：

```bash
低干扰
高信息密度
卡片化
暗色优先
支持浅色
支持模式主题
不炫技
```

Mineradio 的强视觉效果只能进入音乐模式，不应污染学习和开发模式。

### 9.2 信息层级

首页信息优先级：

```bash
一级：
  当前任务
  当前计时
  今日进度
  当前工作模式

二级：
  今日待办
  活动统计
  音乐状态
  ActivityWatch 当前状态

三级：
  趋势图
  历史记录
  详细配置
```

避免首页同时展示太多复杂图表。

### 9.3 卡片设计

统一卡片结构：

```bash
标题
状态/数值
主要操作
辅助信息
```

卡片不应该每个长得像不同项目来的。

统一规范：

```bash
圆角一致
padding 一致
标题字号一致
按钮样式一致
图表色彩一致
空状态一致
加载状态一致
错误状态一致
```

### 9.4 颜色系统

全局 token：

```css
:root {
  --ws-bg: 18 18 22;
  --ws-surface: 28 28 34;
  --ws-panel: 38 38 46;
  --ws-border: 255 255 255 / 0.08;

  --ws-text: 244 244 245;
  --ws-muted: 161 161 170;

  --ws-primary: 132 92 246;
  --ws-accent: 34 211 238;
  --ws-success: 34 197 94;
  --ws-warning: 245 158 11;
  --ws-danger: 239 68 68;

  --ws-radius-card: 18px;
  --ws-radius-widget: 14px;
}
```

颜色使用规则：

```bash
primary：主要操作
accent：当前状态或音乐氛围
success：完成
warning：需要注意
danger：破坏性操作
muted：辅助信息
```

### 9.5 模式主题

内置模式：

```bash
study
coding
writing
music
review
rest
```

每个模式只改变：

```bash
背景
强调色
默认 widgets
动画强度
音乐 mood
```

不改变：

```bash
基础组件结构
按钮逻辑
表单样式
字体体系
```

### 9.6 动效原则

动效只用于表达状态变化。

允许：

```bash
计时器状态切换
音乐播放状态
widget 展开/收起
模式切换
休息提醒
```

禁止：

```bash
无意义背景乱动
学习模式里强粒子动效
按钮过度弹跳
图表频繁重绘
```

### 9.7 响应式设计

至少支持：

```bash
桌面大屏
笔记本 14 寸
平板宽度
窄窗口
```

优先级：

```bash
桌面 > 笔记本 > 平板 > 手机
```

这不是移动端优先产品。

### 9.8 可访问性

必须支持：

```bash
键盘操作
清晰 focus ring
足够对比度
按钮 aria-label
图表文本摘要
减少动画选项
```

## 11. 性能优化

### 11.1 首页性能

首页首屏必须快。

要求：

```bash
首屏优先展示当前任务、计时器、今日摘要
复杂图表延迟加载
ActivityWatch timeline 延迟加载
音乐搜索组件懒加载
设置页懒加载
```

### 11.2 Widget 刷新频率

不同 widget 刷新频率不同：

```bash
当前计时器：1s 前端内存刷新，不每秒请求后端
当前音乐：1s-3s
ActivityWatch 当前状态：10s
token usage：5min
GitHub heatmap：30min
每日汇总：1min 或事件触发
```

### 11.3 后端任务调度

后台任务不要全部同时跑。

建议：

```bash
GitHub 刷新：每 30 分钟
Tokei 刷新：每 5-10 分钟
ActivityWatch 聚合：每 1-5 分钟
数据库清理：每天一次
日志清理：每天一次
```

### 11.4 大数据渲染

ActivityWatch timeline 不能一次渲染上千条。

优化：

```bash
按小时聚合
虚拟列表
只展示 top apps
原始 timeline 放详情页
```

## 12. 安全与隐私优化

### 12.1 本地服务安全

workbench-core 默认只监听：

```bash
127.0.0.1
```

不默认暴露到局域网。

Docker 部署时如需外部访问，必须提示用户配置认证或反向代理。

### 12.2 敏感信息

敏感信息处理：

```bash
GitHub token：不明文入库
音乐 Cookie：不明文入库
API key：不明文展示
导出数据时默认排除凭据
日志中不得打印 token / Cookie
```

### 12.3 隐私设置

用户可以关闭：

```bash
ActivityWatch 原始标题保存
浏览器标题保存
音乐播放历史
token 明细保存
GitHub 原始 payload 保存
```

### 12.4 导出数据

导出时提供两个选项：

```bash
完整导出
隐私导出
```

隐私导出排除：

```bash
原始窗口标题
浏览器标题
音乐搜索历史
Cookie/token
调试日志
```

## 13. 错误处理优化

### 13.1 模块降级

任何外部模块失败，都不能导致整个工作站不可用。

降级规则：

```bash
ActivityWatch 失败 -> 任务和计时器继续
Mineradio 失败 -> 工作站继续
GitHub 失败 -> 显示上次缓存
Tokei 失败 -> 显示错误提示
数据库写入失败 -> 立即提示并进入保护模式
```

### 13.2 错误状态 UI

每个 widget 必须有：

```bash
loading
empty
error
stale
disabled
unauthorized
```

### 13.3 重试策略

API 重试规则：

```bash
本地服务请求：快速重试 2 次
外部网络请求：指数退避
GitHub 请求：避免频繁重试
音乐平台请求：失败后切换候选源
```
